## Narrow RLS and Data API verification checklist

Based on [Supabase's API security guide](https://supabase.com/docs/guides/api/securing-your-api):

1. In a disposable reconstructed or explicitly authorized staging environment, inventory exposed schemas, tables, views and callable functions, effective `anon`/`authenticated`/service privileges, default grants and role membership paths, including inherited and `SET ROLE` access. Preserve the independent strict test; do not assume revoking direct grants removes inherited privileges.
2. Inspect RLS policies and view/function execution context, including `security_invoker` views and `SECURITY DEFINER` functions. Check column-level privileges and owner/service bypass separately. Grants control object reachability; RLS controls rows.
3. With synthetic records and actual test JWTs, exercise the Data API as anonymous, ordinary authenticated, claimant, and administrator: verify permitted exact reads, isolation of private rows, and denied review/claim writes and moderation calls in the default-off state. Verify token and role behavior; local `SET ROLE`/GUC fixtures alone do not validate JWTs.
4. Separately inventory relevant Storage policies, service-role exposure, and the full callable function list. Compare the authorized target's configuration with the reconstructed snapshot and retain unresolved differences as blockers. No hosted database, Auth, API, storage or policy operation was performed here.
