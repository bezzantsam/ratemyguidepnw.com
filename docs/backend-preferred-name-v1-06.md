# Preferred name v1 — backend integration contract

Review-only additive successor to the already applied `e76030edd1cfe5d9b61ef48cf8132a96536f01f13e3030016890ab549b076f78` launch body. It is not a first-launch prerequisite and has not been applied to a hosted database. 01 owns server adapters, UI, search, integration and any later execution; 06 owns this candidate and its backend tests.

## Identity and editing

The input is always an independently reviewed `(jurisdiction, source_id)` resolved through the existing identity map to a published `guides.id`. No preferred name or alias identifies, merges, claims or remaps a guide. Registry name, business, source ID, canonical URL, guide UUID, reviews and claim rows stay unchanged. Inputs require a current confirmed non-anonymous actor, existing launch gate and published mapped guide. Owner edits additionally require the existing approved claim; a guide-row lock serializes writes with ownership decisions. Admin corrections require the existing `public.is_site_admin()` check. Unmapped, unclaimed, unrelated, anonymous, unconfirmed and gate-disabled writes fail closed.

`public.rmg_set_profile_name_v1(p_jurisdiction text, p_source_id text, p_name text)` returns `{ "status": "saved" }` to an approved owner. Null, empty or whitespace-only clears that owner's value. The name is trimmed at both ends using an explicit, locale-independent Unicode whitespace set matching JavaScript `trim()`; the resulting value may contain 1–80 Unicode code points (`char_length`), and `<`, `>` and control characters are rejected. The interface should submit plain text, render as text, and mirror this bound without treating JavaScript UTF-16 code units or grapheme clusters as PostgreSQL code points. The exact normalizer is `rmg_private.normalize_preferred_name_v1` in the candidate.

`public.rmg_own_profile_name_v1(p_jurisdiction text, p_source_id text)` is an authenticated, gate-aware read restricted to the currently approved claimant. It returns `{ "name": string|null, "overridden": boolean }`: `name` is only this actor's stored captain value, even when an admin value wins publicly; `overridden` indicates an active admin correction. It returns null if the declaration belongs to a previous claimant, never returns actor IDs or another claimant's hidden value, and denies unrelated or revoked claimants. Use this private read for the owner editor instead of treating the effective public name as the owner's own input.

`public.rmg_admin_set_profile_name_v1(p_jurisdiction text, p_source_id text, p_name text, p_reason text)` returns the same receipt to an authorized site admin. The optional name follows the same validation and clearing rules. A trimmed, nonempty reason of at most 500 characters with no controls is required for both corrections and clears. Admins can correct an unclaimed but mapped listing. Treat `p_reason` as editorial provenance; Sam's example requires a truthful attribution, not an invented operator verification.

Owner and admin values are separate. An active admin value has display/search precedence. Owner edits remain stored and audited but do not replace the admin value. Clearing the admin value reveals an owner value only if that same declaring actor still has an approved claim; clearing the owner value does not clear the admin value. Revoked/denied claims make the owner's name inactive in public projection. An admin correction can be cleared even if no owner has a value. Writes never affect another guide, the protected canonical name or reviews/claims. Both owner and admin changes, including clear operations, append actor UUID, time, old/new values and origin to the private `rmg_private.profile_name_audit_v1`; admin reasons are recorded there. This is a dedicated private audit because the existing moderation audit restricts target types to reviews/claims. Clients have no direct table or sequence access.

`public.rmg_profile_name_review_v1(p_jurisdiction text, p_source_id text)` is restricted to authenticated, eligible site admins and the enabled gate. It returns `{ "captain_name": string|null, "captain_name_active": boolean, "admin_name": string|null, "history": [...] }`. History contains at most the latest 50 events, newest first; each has `origin`, `old_name`, `new_name`, `reason`, `created_at`. Actor UUIDs remain in the private audit table and are not returned by this API. This supports reviewing a hidden owner edit before clearing or replacing an editorial override; the complete audit remains in the private table.

## Public projection and search

`public.rmg_profile_names_v1(p_jurisdiction text, p_source_ids text[])` is a gated read for anon or authenticated clients. The array must be non-null, contain at most 100 entries, and contain no null/empty or over-100-character source IDs; jurisdiction is exactly `OR` or `WA`. It returns a deterministically source-ID-sorted JSON array of `{ "jurisdiction": "OR", "source_id": "...", "preferred_name": "...", "provenance": "captain" | "admin" }` for mapped, published guides with an active value. Missing, unmapped, unpublished and unset names are omitted. The output never contains account identifiers, reason or audit data. Empty arrays return `[]`. When the launch gate is false the RPC raises `P5030`; a frontend must fall back to existing canonical names and attributed editorial aliases. Do not treat an empty or failed response as proof of a person's legal identity.

For complete directory search, 01 must aggregate all relevant source IDs in bounded batches before applying the preferred-name index; fetching only visible rows would miss other matches. Cache and refresh according to the app's existing safe data boundaries; avoid public caching of private admin responses. Existing `directory-query.ts` caches each `DirectoryEntry` in a WeakMap: construct a new entry when overlays change. Its current ASCII-only normalization removes non-Latin letters; 01 needs Unicode-aware search normalization and appropriate regressions. Keep source aliases in addition to the preferred-name search term.

For the exact source `OG.0000359` Douglas Wolfe / Douglas Scott Wolfe LLC, Sam's separately attributed editorial alias `Scott Wolfe` continues to work regardless of the gate or extension. If the active name is `Scott`, the UI may display **Douglas “Scott” Wolfe** or otherwise follow the approved copy, with the unchanged source name available as “Listed as Douglas Wolfe.” Existing token matching can find `Scott Wolfe` using the preferred and canonical tokens; do not infer another person's surname, copy a family member's profile, or derive IDs from the display. 01 owns actual profile heading, review/claim label, share text and search consistency.

## Compatibility and migration review

The candidate extends `rmg_private.profile_declarations` instead of inventing a separate guide. Existing declaration rows receive `details_declared=true`. A new name-only row receives false; a narrowly compatible `CREATE OR REPLACE` of the existing private `profile_details` respects that marker, and the old `edit_details` signature sets it true when actual details are saved. This prevents a name-only declaration from exposing an older unverified `guide_details` record. Existing public detail RPC signatures and JSON remain unchanged; existing declared details remain visible, and profiles without preferred names behave as before.

`supabase/review-candidates/08-preferred-name-v1.sql` is a single `DO` DDL unit; it expects the launch prerequisite and should not be replayed blindly. `08-preferred-name-v1-disable.sql` revokes only the five new public wrappers and corresponding private functions, leaving names, claims, source mappings and audit intact. The normal launch emergency disable also revokes all private functions; after v1, use the reviewed additive disable when the new public wrapper ACLs themselves must be revoked. Neither disables app flags. Fresh catalog, role/privilege, backup, migration-history, runner compatibility and rollback review remain required before 01 considers a later deployment. A local `psql -1` injection proves rollback of the DDL unit, not exact hosted CLI history/commit semantics.

Run `tests/backend-launch/run-preferred-name-v1.sh` with PostgreSQL 17 and Python 3. It uses synthetic users/guides on a socket-only disposable cluster, applies the exact launch body then the additive candidate, checks failure rollback and the declared owner/admin/denied/Unicode/clear/audit/identity/backward-compatibility behaviors, and tests the additive disable. It preserves its stopped fixture directory for review. It is not a real Supabase Auth/PostgREST/browser test and does not establish a deployed feature. Independent review, exact runner/history tests and integrated frontend/search tests remain outstanding.
