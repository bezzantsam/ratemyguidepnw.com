## Authorization findings

- Captured RLS permits authenticated direct insertion of pending reviews and claims, irrespective of disabled website controls. The throttle is not an IP-aware or concurrency-safe abuse control. Do not treat the UI gate as a backend write gate; a backend lockdown requires independent review and explicit authorization.
- Captured admin RPCs check admin membership but allow an admin to approve their **own** review or claim. [`proposed-no-self-approval.sql`](../scripts/backend-audit/proposed-no-self-approval.sql) is a local-only proposed repair, not a migration. Local tests reproduce both baseline gaps and verify the proposal blocks them while permitting a different administrator to act. It does not solve separation of duties for related accounts.
- The public review and admin pending-review security-invoker views fail with `permission denied for table reviews` in the catalog reconstruction because their underlying column privileges are insufficient. Fix this without exposing `author_id` or private unpublished rows; do not grant blanket table SELECT. Retest public and moderator access against the actual API.
- The approved owner's `guide_details` writes are immediately visible for published guides. Publication moderation and safe target mapping must precede enabling editing. Captured policies allow claimants and admins to read relevant claim evidence; the local role tests exercise both allowed and denied access.
- Admin review approval changes published rating aggregates via the trigger, but the public view grants prevent end-to-end public display. Local tests show pending reviews excluded from anonymous base-table reads and approved reviews included in aggregates.

## Reproducible local checks and limits

Run `scripts/backend-audit/run-local.sh` with PostgreSQL 17 tools (`initdb`, `pg_ctl`, `psql`) and Python 3 on PATH. It creates and destroys a new socket-only local cluster, stubs `auth.uid()` and synthetic `auth.users`, reconstructs the captured subset, and tests anon, two independent users, an approved owner and an admin. It does not read environment files, contact the hosted database, or use real users. It explicitly demonstrates known failures before testing the local-only proposal. This reconstruction does not prove JWT verification, API exposure/configuration, hosted role inheritance, all triggers/extensions, transaction races, actual email/OAuth, or production security. Independent security review, a fresh schema comparison, comprehensive negative/positive API tests, identity review, anti-abuse, and explicit founder release approval remain required.

Supabase's [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) and [API security guidance](https://supabase.com/docs/guides/api/securing-your-api) distinguish table privileges, policies, and invoker-view permissions; testing must cover all three.

## Local repair candidate

[`proposed-authorization-lockdown.sql`](../scripts/backend-audit/proposed-authorization-lockdown.sql) is a review-only SQL proposal, outside the migration directory. It revokes table and column customer DML grants on reviews, claims, evidence, owner details and (if present) guide media, as well as customer execution of the captured moderation and trigger/rating functions. Moderation is default-off even for an application administrator; only a privileged database owner can explicitly grant execution. The proposal retains RLS and adds only specific review-column SELECT grants required by invoker views. Queue views check admin membership, including for draft guides. A claimant retains access to their own evidence, not the administrator queue.

When explicitly granted execution in local fixtures, the revised moderation functions require an authenticated administrator and a non-null decision, reject non-pending targets and self-approval, and prevent an approved owner from moderating either outcome on their own guide. Review decisions and ownership approvals serialize on the target guide. The claim's target row is locked and rechecked, and the captured partial unique index remains a second ownership guard. Status changes, aggregate triggers, and moderation audits are one transaction; the tests inject an audit failure to verify rollback.

The harness runs three states: (A) the original captured baseline and its unchanged reproduction tests; (B) the proposal in a separate reconstructed database, with writes and moderator RPCs disabled but published reviews and restricted administrator queues readable; and (C) explicit local-only moderation grants and synthetic fixtures, including two concurrent database sessions competing to approve different claims on the same guide. The runner confirms the second session actually blocks, then checks one approval, one unchanged pending claim and one audit record. An application administrator is not the privileged database owner used solely to set up fixtures and grant the local experiment.

Limitations: the captured subset does not contain the hosted `guide_media` definition, storage policies, all callable functions, role memberships, or Data API exposure settings. The media table used in these tests is expressly synthetic, and the candidate does not address storage-object writes or service-role/owner privileges. Before any hosted application, independently inspect the full current schema, role inheritance, every write-capable function and storage policy; reconcile the schema fingerprint; validate genuine Supabase Auth/JWT, anonymous sign-ins, Data API grants and real role behavior; separately review rate limiting, abuse controls and identity mapping; and obtain explicit release approval. This local candidate does not enable customer writes or authorize a hosted migration.
