# Disposable real Auth/PostgREST fixture (candidate; CI execution required)

This is independent of hosted Supabase. Run only on a fresh, disposable GitHub-hosted Linux x86_64 runner with Docker, at least 8 GiB free on Docker's filesystem and 1 GiB in runner temp. It creates a unique unlinked local Supabase project, uses pinned CLI 3.2.0 with a verified archive, runs actual local Auth, PostgREST and Mailpit, and applies the exact candidate to reconstructed synthetic application tables. It does not contact hosted databases or send external email. No CLI log or status file may be published as an artifact: they contain local credentials. This harness has not yet passed a real CI run.

Only in the generated disposable configuration, the local Auth email send limit is set to 20 per hour to allow four synthetic confirmations through Mailpit. Product/database abuse controls and hosted configuration are untouched.

01 owns the guarded workflow and pins the checkout to the reviewed tree. On a fresh GitHub-hosted runner, after including 05's independent assertion file at a pinned path, the job's essential step is:

```yaml
permissions:
  contents: read
jobs:
  local-auth:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
      - name: Local synthetic Supabase Auth and PostgREST
        shell: bash
        run: bash tests/backend-auth-local/run-ci.sh "$GITHUB_WORKSPACE/PATH-TO-05-ASSERTIONS.py"
```

Replace the path with 05's reviewed, checked-in script; do not substitute an empty test. Disable shell tracing. The runner receives `RMG_LOCAL_STATUS_FILE`, an owner-only JSON file generated by `supabase status -o json`, and `RMG_LOCAL_PROJECT`. Status fields are `API_URL`, `DB_URL`, `MAILPIT_URL`, `ANON_KEY` and `PUBLISHABLE_KEY`; use the local anon key for `/auth/v1/*` and `/rest/v1/*`, Mailpit's local API under `/api/v1/`, and the local DB only for controlled synthetic setup and assertions. Recheck every endpoint is loopback before use. Do not print response bodies containing addresses, tokens or links. The database gate starts false; test that behavior before setting it true in the disposable fixture. Create test accounts through actual local Auth and designate a synthetic moderator in `public.site_admins` only after obtaining its local UUID. Use fictional guides `OR/fixture-one` and `OR/fixture-two`; no actual names, registrations or user records are loaded. Validate email confirmation, auth sessions, actor isolation, operator authorization, persistence, review edit moderation and original published content. Explicitly return a nonzero status for each failed check.

For an earlier setup-only run, use `bash tests/backend-auth-local/run-ci.sh "$GITHUB_WORKSPACE/tests/backend-auth-local/smoke.py"`. It verifies that the schema loaded and local Auth, PostgREST and Mailpit return HTTP 200. It is not the 05 acceptance suite and does not verify sign-in or application authorization.

To rehearse CLI migration history and atomic failure on a separate fresh runner, use `RMG_FIXTURE_SCHEMA_ONLY=1 bash tests/backend-auth-local/run-ci.sh "$GITHUB_WORKSPACE/tests/backend-auth-local/migration-history.py"`. It asks the CLI to create its own timestamped migration, injects a failure into the exact runner-managed body and checks schema, public catalog and history were rolled back, then applies the unmodified body and checks history and default-off gate. This tests the local CLI only; it does not prove Management API transaction semantics or resolve the hosted history mismatch.

The runner discards its VM and private temporary files at job end; it does not touch any existing machine's Docker state or prune images. A failed setup prints a safe high-level stage and exits nonzero; sensitive local CLI logs remain private on that ephemeral runner. This is a synthetic service test, not a hosted Auth configuration, hosted Storage acceptance, production deployment, or operator-account verification.
